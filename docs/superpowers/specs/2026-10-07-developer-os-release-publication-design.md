# Developer OS — Release Publication Design (A16)

**Status: approved by the founder on 2026-10-07 (design in conversation, written spec reviewed the same day); §3.3 added 2026-10-08 from the Task 11b packer, awaiting ratification.** This is
`ORDER.md` entry A16 (DOS-P9, program plan Task 9: `git show
ae25acd9:docs/superpowers/plans/2026-07-21-developer-os-program.md`). It covers publication only.
The update side, the packed release format and the packer belong to Spec 2's block "Amended 2026-10-07
(D84, Task 11b)" (K1–K6), which this specification consumes and does not restate (founder decision
2026-10-07: whoever owns the packer owns the format).

## 1. Scope

In scope: building the release tarballs, the GitHub Release, the Homebrew tap and its formula, the
release gates, the public documentation set of program plan Task 9, the beta, and `v1.0.0`.

Out of scope: the bundle format, the keg layout and `update` behaviour (Spec 2 K1–K6); signing (D46,
D84 (1): the channel is the trust root); telemetry (none exists, so the beta collects only issues that
participants report).

Blocked by: **L1** (the exact OSI license text, approved with qualified counsel) before any public
release, beta included, because a formula in a public tap is distribution and carries a `license`
field; **L2** (the tap repository, the `TAP_PR_TOKEN` secret, Actions release permissions); Task 11b
(the packer and keg admission).

## 2. Pipeline

Two founder approvals gate every release. Nothing reaches a user before both.

1. **Tag.** The founder pushes `vX.Y.Z` on a commit of `development`. `X.Y.Z` is canonical stable
   semver (Spec 2 §4.3).
2. **Preflight** (`.github/workflows/release.yml`, `on: push: tags: ['v*']`). It confirms that the
   tag's commit has a completed, successful `check.yml` run, queried through the GitHub API. It never
   reruns the full suite, which takes about 4 h, and it refuses a tag without that run. It also runs the
   pinned history secret scanner (§5) over the full history at the tag.
3. **Build.** A matrix of one Apple Silicon macOS runner and one Intel macOS runner. The exact labels
   are verified against GitHub's current runner list when the plan is written, because Intel labels are
   being retired. Each job checks out the tag, runs `pnpm install --frozen-lockfile`, then runs the Task
   11b packer with `--architecture <arm64|x64> --version X.Y.Z --release-sequence <§3.2>`. The packer
   downloads the official Node 24 `darwin-<arch>` archive from `nodejs.org` and verifies it against a
   SHA-256 pinned in the repository (taken from that release's `SHASUMS256.txt`), so the runtime is never
   trusted from the network alone. The output is
   `developer-os-X.Y.Z-darwin-<arch>.tar.gz`, deterministic: sorted entries, fixed owner `0:0`, fixed
   mtime equal to the tag commit's time, modes `0755`/`0644`, and `gzip -n`. Rebuilding the same tag
   produces identical bytes.
4. **Verify.** On each runner the job unpacks its tarball into a scratch prefix and runs the K2 keg
   admission against it; any failure fails the release. A negative step flips one byte of a bundled
   file and requires the admission to refuse.
5. **Draft.** A publish job (the only job with `permissions: contents: write`) creates a **draft**
   GitHub Release `vX.Y.Z` with the two tarballs, `SHA256SUMS`, and a CycloneDX SBOM generated by
   `@cyclonedx/cdxgen`, an exact root devDependency whose whole tree the lockfile pins (amended
   2026-10-09, NEW-201), run with `pnpm exec` after a frozen install. It is a CI tool, not a product
   dependency. The release notes are the `CHANGELOG.md` section for `X.Y.Z`; a missing section
   fails the job.
6. **Approval 1.** The founder reviews the draft and publishes it. Assets only get public URLs once the
   release is published.
7. **Tap PR** (`.github/workflows/tap.yml`, `on: release: types: [published]`). It downloads only
   `SHA256SUMS` from the published release, not the tarballs: the publish job already re-verified the
   tarballs against it (step 5), and the formula needs only their hashes. Two jobs split the trust, as
   `release.yml` does. The `edit` job (no environment, read-only token, no secret) runs
   `.github/release/update-formula.sh` fetched at the event commit, which rewrites `version`, both
   `url`s and both `sha256`s of the tap's existing `Formula/developer-os.rb`, and uploads only that file
   as an artifact. The `push` job (`environment: tap`, `needs: edit`) runs no repository code: it clones
   the tap fresh, accepts exactly that one file from the artifact, re-checks that the diff is exactly
   five changed lines of `Formula/developer-os.rb`, and pushes and opens a pull request in
   `msolecki/homebrew-developer-os` with absolute-path `git` (hooks disabled) and `gh`. Only that job's
   last step sees `TAP_PR_TOKEN`, a fine-grained token limited to that one repository with contents and
   pull-request write access.
8. **Approval 2.** The founder merges the tap PR. That merge is the release: `brew upgrade` sees it.

A failed or abandoned release is withdrawn by deleting the draft or closing the tap PR. A published but
unmerged release reaches no user. A merged formula is rolled back by reverting the tap commit. Users
already updated keep their `update rollback` path (Spec 2 §10).

## 3. Formula and versions

### 3.1 Formula

```ruby
class DeveloperOs < Formula
  desc "Shared workflows and a local-first knowledge base for Claude Code and Codex"
  homepage "https://github.com/msolecki/developer-os"
  version "X.Y.Z"
  license "<L1>"
  on_arm do
    url "https://github.com/msolecki/developer-os/releases/download/vX.Y.Z/developer-os-X.Y.Z-darwin-arm64.tar.gz"
    sha256 "<arm64>"
  end
  on_intel do
    url "https://github.com/msolecki/developer-os/releases/download/vX.Y.Z/developer-os-X.Y.Z-darwin-x64.tar.gz"
    sha256 "<x64>"
  end
  depends_on :macos

  def install
    libexec.install Dir["*"]
    bin.install_symlink libexec/"bin/developer-os"
  end

  test do
    assert_match version.to_s, shell_output("#{bin}/developer-os --version")
  end
end
```

The formula has no `depends_on "node"`, because the runtime is inside the bundle (K2), and no
`post_install` step: the formula never runs product code at install time. The tarball's top level
holds the launcher at `bin/developer-os` and the packaged release at `fallback/`, so the keg has
`libexec/fallback`, which is K2's fixed path. Homebrew keeps the archive's `0755`/`0644` modes, which
K2's source admission accepts.

### 3.2 Versions and sequences

`releaseSequence` = `major × 1,000,000 + minor × 1,000 + patch`, with minor and patch below 1,000.
It increases strictly with semver and needs no stored state. `releaseIndexSequence` equals it. Beta
releases are `0.Y.Z` in the same tap, and every beta after the first reaches its testers through
`update`. `1.0.0` is tagged when the beta has no open release blocker and L1 and L2 are closed.

### 3.3 Amended 2026-10-08 (Task 11b implementation; awaiting founder ratification)

The packer that Task 11b built (`npm run pack:release`, `tests/tools/pack-release.ts`) changes three
details of §2 and §3.1:

- **One packer run builds both architectures** (D96 Q2). It writes each keg tree with `bin/developer-os`
  and `libexec/{launcher.mjs, fallback/}` at the keg root, plus each bundle's `.tar.zst` archive and
  manifest under `archives/<version>/`. The release tarball therefore holds the keg root itself, and
  the formula installs it with `prefix.install Dir["*"]` rather than `libexec.install`. §2 step 3's
  per-architecture matrix becomes one macOS job; the two tarballs are still published separately.
- **Node is a packer input, never fetched by the packer.** Each slot is `{path, sha256, version}`. The
  workflow downloads both official Node 24 `darwin` archives and passes the SHA-256 pinned in the
  repository. The packer runs `--version` only on the host-architecture binary, so any macOS runner
  works; the zstd bytes depend on the Node that runs the packer, which the workflow pins.
- **Clean tree, no revisions.** `release.yml` never passes `--allow-dirty`; the packer refuses that flag
  when `CI` is set (`tests/tools/pack-release.ts`, `assertCleanCheckout`). The formula never uses Homebrew's `revision`: the launcher admits only
  `Cellar/developer-os/<stable-semver>` kegs, so a `1.2.0_1` keg would remove the fallback. Installed
  metadata is mode `0644` and directories `0755`, which the launcher and K2 admission require.

### 3.4 Amended 2026-10-08 (A16 plan rulings; awaiting founder ratification)

- §2 step 3 and §3.1 are read through §3.3: one packer job, no `--architecture` flag, Node passed in,
  and the formula installs the keg root with `prefix.install Dir["*"]`.
- The repository pins each Node archive's SHA-256 from `SHASUMS256.txt`; CI verifies the archive,
  extracts `bin/node`, and passes that binary's own SHA-256 to the packer.
- The per-bundle `.tar.zst` archives the packer writes describe the index rows' archive fields and are
  not published; the release assets stay the two tarballs, `SHA256SUMS` and the SBOM.
- §5's clean-account gate runs in a fresh macOS VM (D96 Q5), not a second account.
- A tag is released only from a `development` commit that has its own successful `check.yml` push run.
- Known risk, proven only by the VM gate: Homebrew's install-time relocation or re-signing must leave
  `libexec/fallback` byte- and mode-identical, or K2 admission refuses every real install.

## 4. Documentation set

These are created before the first beta, as listed in program plan Task 9: `README.md`, `SECURITY.md`
(private reporting through GitHub security advisories), `CONTRIBUTING.md`, `CHANGELOG.md` (one section
per version; the release job requires it), `LICENSE` (the L1 text), `docs/install/` (Homebrew install,
`init`, upgrade, rollback, uninstall), `docs/tutorials/` (Claude-only, Codex-only and dual-agent),
`docs/troubleshooting/`, and `docs/privacy.md`. The privacy page lists every network action:
Homebrew's download, and the vendor CLIs the user runs. The product itself makes none.

## 5. Verification

- **CI, per release:** the preflight `check.yml` gate, the history secret scan, the determinism check
  (the tarball's SHA-256 is computed twice from two packer runs in the same job and must match), the K2
  admission of each tarball and the negative byte-flip check.
- **Repository tests (Task 11b and this plan):** the formula renders from a template with exact values
  (a unit test renders it and compares); `releaseSequence` arithmetic, including the 1,000 bound,
  which refuses rather than wraps.
- **Secret scan:** a pinned `gitleaks` version runs over the full history in the preflight. Its
  allowlist lives in the repository and every entry carries a reason. It runs before the first beta
  tag and on every tag after.
- **Clean-account gate (founder):** on a disposable macOS account, for each beta and for `1.0.0`:
  `brew tap msolecki/developer-os`, `brew install developer-os`, `developer-os init`, then
  capture → review → ingest → search, then `brew upgrade` to the next beta, `developer-os update
  --apply`, `developer-os update rollback --apply`, and finally `developer-os uninstall`. The Brain must
  survive with every file's hash unchanged.
- **Beta:** invited participants use synthetic or their own vaults. Issues come only from what they
  report. Each release blocker goes through the normal spec and plan flow, and the matrix is run again.

## 6. Accepted residuals

- Whoever controls the GitHub repository's releases and the tap controls updates (Spec 2 K1). There is
  no transparency log and no signature, by founder decision (D46, D84).
- The Node runtime's integrity rests on the SHA-256 pinned in the repository, which was copied from
  nodejs.org's `SHASUMS256.txt`. Its GPG signature is not verified in CI.
- GitHub-hosted runners are trusted to build. Rebuilding a tag and comparing bytes is the
  reproducibility check: anyone can run the packer at the tag and compare against `SHA256SUMS`.
