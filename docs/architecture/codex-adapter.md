# The Codex adapter

`packages/adapter-codex` and the generated `plugins/codex/`, delivered by DOS-P5 on 2026-08-12.
The same canonical workflow that becomes a Claude Code skill becomes a Codex plugin, and nothing
about Codex leaks into any other package.

This note absorbed the surviving design record on 2026-08-24, when the completed subsystem spec
was deleted. It includes the four amendments forced by first contact with a real binary (§7) and
the DOS-P6 correction: capture is agent-authored, hooks and the `developer-os run codex` wrapper
are declined, and the six unused capability keys resolve to `not-used`. The implementation plan
was deleted when its last step closed; git history is the archive for both.

**Read `docs/architecture/claude-adapter.md` beside this.** The two adapters are peers with one
consumer, and half of what is true here is true there for the same reason. Where a decision now
covers both — no hooks, `plugin_hooks` is `not-used`, one skill body, one capability vocabulary — this
note says so rather than restating it as a coincidence.

## 2. What it cannot do, on purpose

1. **It ships no hooks.** `hooks/hooks.json` is not emitted. §5 carries why, and the decision now
   covers both adapters rather than either alone.
2. **It never writes `AGENTS.md`, and never `AGENTS.override.md` at any scope.** The second is the
   important one: in the global scope Codex reads `AGENTS.override.md` *instead of* `AGENTS.md`, so
   writing one would silently suppress the user's own instructions. It is the single most
   destructive thing this adapter could do to a configuration, and it is refused rather than merely
   omitted. `durable_project_guidance` is therefore reported and used by nothing (§11.5).
3. **It never reads or writes `~/.codex/config.toml`.** The vendor's CLI is the only writer of the
   vendor's config (§4). Verified by write-ordering against a real installation: no `config.toml`
   exists after this adapter writes its tree, and one appears only after `codex plugin marketplace
   add` runs.
4. **It never opens `transcript_path`**, on any code path — enforced by
   `tests/repository/transcript-path.test.ts`, added 2026-08-12, which fails if that field name
   appears anywhere under `apps/`, `packages/`, `tests/` or `workflows/`. Before that test existed
   this claim was backed by a grep a reviewer ran once, which is a convention, not a gate. Codex
   puts the field in every hook payload, so the file is one `readFile` away at all times; the
   refusal may be lifted only by an amendment naming a stable documented contract and landing a
   regression fixture in the same change.
5. **Three flags are refused permanently, by test rather than by convention:**
   `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-bypass-hook-trust` and
   `--ignore-user-config`. `danger-full-access` is unreachable *by construction* rather than
   unwritten — the sandbox mode is chosen from the declared write-scope count, never from an
   argument.
6. **The managed-hook trust bypass is not offered.** `requirements.toml` would let our hooks skip
   the vendor's consent prompt. Routing around a gate the vendor placed deliberately is the wrong
   default for a product whose pitch is that it does not surprise you. Not offered, not
   configurable, not in v1.
7. **It executes no workflow verb.** A rendered skill is guidance; the effects it names are
   `developer-os` commands. DOS-P6 shipped the capture, ingest, review and Brain commands; only
   `agent.prompt` still lacks a step executor — §10.
8. **It spawns no process itself.** Execution goes through `packages/security`'s runner, and the
   two `codex plugin` steps are *proposed*, not run, by this package.

## 3. The capability model — two gates, three values, and one observable key

`yes` requires a documented version floor to permit the capability **and** a probe to observe it.
A probe that could not run yields `unknown`. DOS-P6 removed `wrapper-required`: `plugin_hooks`,
`session_start_injection`, `session_end_capture`, `pre_compact_backup`, `subagents` and
`durable_project_guidance` are unused by this product and resolve to `not-used` before either gate.
Both adapters share this vocabulary and their key lists are asserted equal.

**The probe is genuinely better here.** `codex plugin list --json` settles three questions in one
structured call — installed, enabled, and whether the resolved path is the tree we own — where
Claude needed a separate settings read to distinguish presence from enablement.

**Only `skills` is observable.** No probe reaches a lifecycle event, and the six unused keys short
circuit to `not-used`. DOS-P6 connected both probes to `developer-os doctor --probe`, so the
two-gate machinery now has a production caller; without `--probe`, doctor reports the bounded
unprobed state rather than pretending to have observed a vendor capability.

**`plugin_hooks` is `not-used` in both adapters.** Neither adapter ships a hooks file, and DOS-P6
declined automatic capture after proving a session-end hook cannot supply the required agent-authored
text without reading `transcript_path`. Removing a key from either `NOT_USED` list requires, in the
same change, the artifact or behaviour it describes and a test that observed it working.

**The two key lists must stay identical, and a test now says so.** `CODEX_CAPABILITY_KEYS` and
`CLAUDE_CAPABILITY_KEYS` are spelled out separately because the two packages may never import one
another — so neither package can assert the property about itself. The assertion lives in
`apps/cli/src/adapter-capability-parity.test.ts`, the one place both adapters are legally visible
at once. Before it, both files carried prose claiming the lists were identical and nothing checked
it. **Owner of keeping them so: DOS-P6**, as the consumer the parity exists for.

**The floor is `0.147.0`, and it is one observed version, not a range.** DOS-P5's Task 17 ran the real
install path against the one Codex available and raised the floor to it. This is a *raise* rather
than a confirmation of the prior `0.144.6`: that same task fixed three real bugs in this adapter's
own CLI argv and marketplace document (§7) without which no install step succeeded at all, so
nothing establishes those corrected commands ever worked below `0.147.0` — that version predates
the observation entirely and may not carry the `plugin` subcommands this design depends on.
**Owner: DOS-P9**, whose supported-version matrix is where a range is established or narrowed.

## 4. The install shape — a local marketplace, and what it buys over a cache copy

Codex has no in-place plugin discovery equivalent to the mechanism DOS-P4 uses. It has a
marketplace, and a marketplace may be **local** — which resolves an installed plugin to its real
on-disk path rather than to a cache copy. That is the same property that decided DOS-P4, reached by
a different route, and it is the single most important sentence in this note for anyone changing
the install.

```text
<product-home>/codex/                     ← the marketplace root
├── .agents/plugins/marketplace.json      ← generated at install time, never checked in
└── plugins/developer-os/                 ← the plugin root
    ├── .codex-plugin/plugin.json
    └── skills/developer-os-<id>/SKILL.md × 6
```

`init` runs two steps through the security runner, behind explicit consent — `codex plugin
marketplace add <marketplace-root>`, then `codex plugin add developer-os@developer-os --json` —
and uninstall reverses them before the tree is deleted, because a marketplace registered against a
directory we removed is a worse state than leaving both. The proposal carries a `registrationPhase`
field so an apply-phase caller reads the ordering rather than remembering it; getting it backwards
on uninstall is exactly the failure the ordering exists to prevent.

**The real binary confirmed what the shape was chosen for.** `codex plugin list --json`'s
`installed[].source.path` for our plugin is the tree this adapter wrote, never the separate cache
copy `codex plugin add` also stages. `probeCodex` compares against that field, which is the only
reason it can tell our tree from an artifact somebody else installed under our name. **This is a
hazard, not a caveat, and it now has an owner.** `codex debug prompt-input` resolves each skill's
file locator to the *cache* copy, not to the tree this adapter wrote and hashes — so an in-place
re-render of the plugin tree may never reach the model until some unobserved resync. That is the
update lifecycle, DOS-P7, and the cutover, DOS-P8: §11.14 carries the residual and §12 tells DOS-P8
what it must know.

**We never merge the vendor's config.** A hand-rolled TOML merge against a file whose schema we do
not own is a drift generator, and `--strict-config` exists precisely because that file's recognized
fields change between versions. DOS-P4 stayed out of `settings.json` by writing nothing; DOS-P5
stays out of `config.toml` by delegating the write. `buildConflictEvidence` therefore has no
consumer in either adapter (§11.9).

### Two roots, now distinct types — the closed mistake this subsystem made twice

`RenderedArtifact` once described artifacts relative to **two different roots**.
`renderCodexPlugin` returns branded `PluginRootArtifact` paths relative to the plugin root —
`.codex-plugin/plugin.json`, `skills/…` — and that is what `plugins/codex/` checks in.
`renderCodexInstallTree` returns branded `MarketplaceRootArtifact` paths for the marketplace root,
which is what `proposeCodexInstall` accepts.

**The plugin root is a descendant of the marketplace root, so a wrongly-rooted path does not
refuse.** Containment passes, the tree lands one level too shallow or one level too deep, and it
applies cleanly. **This subsystem made that mistake twice, in opposite directions**: the install
proposal was first rooted at the plugin tree, so the descriptor was never proposed at all and
`marketplace add` would have registered a directory containing no `marketplace.json`; correcting
that then left `buildPluginTree`'s output under-nesting until `PLUGIN_TREE_PREFIX` was derived.
Neither was caught by containment, because containment is not the guard here.

`PLUGIN_TREE_PREFIX` (`plugin.ts`) is the single re-root, derived from `PLUGIN_TREE_SEGMENTS`;
`renderCodexInstallTree` (`compose.ts`) is the only place it is applied. The distinct brands make a
plugin-root tree a compile-time error at `proposeCodexInstall`, while the runtime guard still
refuses a brand erased or forged across a JavaScript boundary. The façade binds
`renderInstallTree`, not `renderPlugin`. This closes `BACKLOG.md` NEW-13.

## 5. `hooks/hooks.json` is not shipped — one decision covering both adapters

The first no-hooks decision was ratified on 2026-08-12. DOS-P6 then settled the product decision on
2026-08-13: **hooks are declined, not deferred**, in both adapters.

The blocker was not an executable bit; a `"type": "command"` hook accepts a command string. The
capture workflow requires agent-authored observation text, while a session-end hook can supply no
such text without opening `transcript_path`, which this product refuses on every code path. A hook
would therefore have nothing faithful to capture. `developer-os run codex` was declined with it.

Tests assert that no hooks ship and that the affected capability keys resolve to `not-used`.
Codex's managed-hook trust bypass remains refused; if a future design reintroduces hooks, the founder
must grant trust manually. That future work requires an explicit amendment and an observed test; it
is not outstanding DOS-P6 work.

## 6. Rendering — the skill body is shared

**The two adapters differ only in frontmatter, artifact path and manifest.** The body — the
preamble, the refusals, the steps, the recovery block, the screen seam and the overlay call — comes
from `renderSkillBody` in `packages/workflow-schema/src/skill.ts`, moved there by DOS-P5 Task 3 and
ratified by the founder on 2026-08-12. `CodexRenderer` is under thirty lines of real code.

**A Codex renderer written the obvious way would have been a byte-for-byte copy of the Claude
one.** Codex's required frontmatter is `name` and `description` — exactly Claude's — and both write
`skills/developer-os-<id>/SKILL.md`. Some four hundred lines and twenty tests would have been
duplicated across two packages that may not import each other, including a security screen and a
fail-open fix that had already been caught once. The proof the move preserved behaviour is one
command: `npm run render:claude` left `plugins/claude/` byte-identical. **Any later change to the
shared body owes the same proof, for both trees.**

Three consequences a reader of either spec alone would get wrong:

- **A vendor renderer screens only what it renders itself.** `recovery.resume`, `id`,
  `refusals[].message` and `steps[].prose` are screened inside `renderSkillBody`, before either
  adapter sees them. `CodexRenderer` screens `description` alone, bounded by the compiler's
  `SKILL_FIELD_CAP` so both vendor trees truncate a long one at the same place. Re-screening in the
  adapter would be a second copy of the seam the move existed to remove. Both specs carry a dated
  amendment saying so.
- **The frontmatter is built from the pre-overlay contract and the body from the post-overlay
  one.** That is safe only because `workflowOverlaySchema` cannot reach `id`, `version` or
  `description`, an invariant that schema's own docblock and `overlay.test.ts` pin. Do not "fix" it
  by moving the frontmatter.
- **The description is emitted through `JSON.stringify`**, which is a valid YAML double-quoted
  scalar. A bare `description: capture: a learning` is a nested mapping and the skill silently does
  not load.

**The manifest is the one place the two adapters answered the same question differently.** Codex's
`.codex-plugin/plugin.json` carries `name`, `version`, `description` and `skills`; Claude's
`.claude-plugin/plugin.json` carries `{ name }` alone. Both are minimal against their own vendor's
documented requirement, both are proven against the real vendor, and the difference is
spec-mandated rather than drift — but it is the one asymmetry in an otherwise identical pipeline,
and it is recorded here so DOS-P6 does not read it as a bug. `PLUGIN_VERSION` and
`PLUGIN_DESCRIPTION` are literals with nothing tying them to `package.json`, matching this
repository's existing convention.

**Determinism.** `buildPluginTree` sorts by code point, so the six workflows produce the same bytes
in any directory order, and it refuses two artifacts claiming one path — a skill's path is built
from the workflow's `id`, which comes from the YAML rather than the directory it sits in. This is
the other half of the byte-identity debt `workflow-schema.md` §6 assigned to DOS-P4 and DOS-P5; it
is now paid on both sides.

## 7. Invocation

```text
codex exec --json --output-schema <schema-file> -s <sandbox> [--add-dir <dir>]... \
           --skip-git-repo-check -C <working-root> <prompt>
```

The sandbox comes from the declared write-scope count: none → `read-only`, one or more →
`workspace-write` plus `--add-dir` naming exactly those scopes. `--output-schema` constrains the
model's final response and the result is validated afterwards anyway: constrain, then validate.
Every value position goes through a screen from `@developer-os/security` — one copy of each, shared
with the Claude adapter since Task 3.5 — and **which screen depends on where the value came from**.
A write scope originates outside this repository and keeps both rules (`screenValueArgument`); the
prompt is prose and keeps the positional rule alone (`screenProseArgument`); the working root and the
output schema path are assembled by this product and also keep the positional rule alone
(`screenDerivedPathArgument`). That last split closed `BACKLOG.md` §1 NEW-12 on 2026-08-17: applying
the *nominal* half to a path derived from the user's own `brainPath` refused a vault at
`~/Danger/DeveloperBrain` permanently, and applying it to a capture body refused every observation
that quoted an `EACCES` message.

**This package does not write the file `outputSchemaPath` points at.** DOS-P6 closed the product
obligation outside the adapter: `init` embeds and installs one managed schema per structured-result
verb, and `ingest` derives the installed path from product state and selects it for the invocation.
`invokeCodex` only screens that path, places it in argv, and never reads or creates the file. A
missing path therefore remains the caller's error and produces `codex exec`'s non-zero `exit`
variant, never `malformed-output`. §11.13 records the closed split of ownership.

**`agent.prompt` is one schema for one verb.** `parseAgentPromptArgs` lives in `packages/core` and
both adapters import it; two adapters with two argument schemas would be a workflow that validates
against one vendor and not the other. Refusals never echo the rejected value, because a `with`
block is author-controlled and the message reaches a log.

**The direct adapter APIs remain asymmetric; the shared workflow parser fails closed.**
`ClaudeInvocation.maxTurns` is bounded from 1 through 50, while `CodexInvocation` has no turn field.
`parseAgentPromptArgs` therefore refuses a workflow-supplied `maxTurns` outright, so no canonical
workflow can silently apply a bound on Claude and drop it on Codex. What remains is the direct-call
asymmetry for a future cross-vendor executor to resolve. **Owner: DOS-P7.**

**Historical, superseded rule.** The first JSONL implementation reduced `codex exec --json` stdout
to **the last line that parsed as a non-null JSON object** before `parseStructuredPayload` saw it.
That rule was provisional because no successful real stream had been observed; handing raw stdout
straight through would instead have made every real invocation report `malformed-output`. Settling
the terminal event required one real `codex exec` call, which invokes a model on the founder's
credentials and costs money — **declined by the founder for DOS-P5 on 2026-08-12**, whose Task 17
therefore stayed scoped to offline plugin management. The current contract is the
`finalAgentMessage` selection stated below: `item.completed` / `agent_message` / string `text`.

**DOS-P6's Task 17 made that call on 2026-08-15, and the rule was half settled.** This section carries
the dated amendment and `tests/fixtures/codex/observed-exec-stream.jsonl` is the recording. The
framing is **confirmed** — one JSON object per line — and so is the existence of a discriminating
field, `type`, present on every line, with an observed vocabulary of `thread.started`,
`turn.started`, `error` and `turn.failed`. What that run could not settle was whether a *successful*
turn's terminal event is the final response: it ended `turn.failed` on an exhausted usage limit, so
no run reached a model response.

**NEW-21 settled it on 2026-08-20, and the answer was that the rule was wrong.** A successful turn
ends on `turn.completed`, which carries a `usage` object and nothing else; the response is the event
before it — an `item.completed` whose `item.type` is `agent_message`, holding the schema-constrained
JSON as a **string** in `text`. `finalJsonlLine` took the last parsing line, so it returned the usage
record and `parseStructuredPayload` returned that as `ok: true`: a caller told nothing had failed,
holding vendor telemetry with no proposal in it. **The failure was silent, total, and green** — every
successful Codex ingest would have produced it, and no gate could see it, because no fixture in the
repository had ever contained a real successful stream. The recording now is
`tests/fixtures/codex/observed-exec-success-stream.jsonl`.

**`finalAgentMessage` replaces it**, selecting on `item.completed` / `agent_message` / `text`. That is
a narrowing this design requires to be proven against a stream where old and new rules agree, and no
such stream exists or can: the old rule is not narrower, it is wrong, and the two disagree on every
successful turn. What is given up is one input class — a bare JSON object on stdout, a shape no
observed run produces. What is bought is that a vendor rename now yields `malformed-output` rather
than a confident wrong answer. **`--output-last-message` was tested and works**, and was declined
because it adds a vendor-written temp file this product would have to own; this section records why, so
that whoever reopens the rule knows the alternative exists.

### The four design amendments of 2026-08-12

First contact with a real `codex-cli 0.147.0` contradicted the design four times, three of which
stopped the install completing at all. All four are carried here;
they are listed here because they are the difference between a design that reads plausibly and one
that runs.

1. **`source.path` in the marketplace document must be `./`-prefixed and marketplace-root-relative.**
   An absolute path — which is what shipped — does not error. The marketplace loads cleanly and the
   plugin entry is **silently dropped** from both `available` and `installed`, after which
   `plugin add` refuses with "not found in marketplace". A relative path without the leading `./`
   fails identically. The marketplace root is the directory passed to `marketplace add`, *not* the
   directory `marketplace.json` lives in, which is two levels below it.
2. **`codex plugin marketplace add` takes exactly one positional argument**, the source path. The
   two-argument form the spec showed refuses with a usage error; the marketplace's name is read from
   the document's own `name` field.
3. **`codex plugin remove` requires the qualified `<plugin>@<marketplace>` form once more than one
   marketplace is configured.** A bare name refuses only under that condition — DOS-P5's Task 17 observed
   `codex plugin remove developer-os` exit 1 with `plugin requires --marketplace unless passed as
   <plugin>@<marketplace>` once a second marketplace existed to disambiguate against; `install.ts`
   carries the condition precisely, and this note previously stated the refusal as unconditional.
   Separately: it does not verify the plugin was ever installed under that marketplace, so
   removing a name nothing added still exits 0 — a failure of that step cannot be produced by naming
   the wrong plugin.
4. **`codex plugin list --json` returns `{ installed, available }`**, each entry carrying `enabled`
   and a **nested** `source.path` — not the guessed `{ plugins: [{ status, path }] }`. Against that
   real shape the probe's original schema would have reported `skills: unavailable` on every real
   installation, and the two-gate model would have resolved `skills` to `unknown` forever. Caught by
   inspection rather than by a failing test, because the integration test drives the CLI directly.

## 8. Regenerating the tree

Run `npm run render:codex`. The drift check in `tests/contracts/adapters/codex/generated.test.ts`
is what turns forgetting into a red build, and it was watched go red both ways — a changed byte and
an extra file — because a gate nobody has watched fail is a gate about a false property. It asserts
set equality as well as per-file identity, since `detectWorkflowDrift` iterates the expected side
only and would say nothing about a file on disk no render produces.

`plugins/codex/` exists only in a source checkout, so its regenerator belongs to the repository
rather than to the product — the same reasoning `claude-adapter.md` §7 records for declining a
`workflow render` CLI verb. The composition itself stays in the package, so the regenerator and the
drift check call one function.

**The `tests` workspace resolves this package through `dist`.** A bare `pnpm vitest run` therefore
checks the checked-in tree against the *last built* renderer, and a src-only mutation used to prove
a gate goes red can lie. `npm run check` builds first; trust that, not an ad-hoc run.

## 9. What DOS-P6 inherited — the two-adapter table

The completed design's table, updated with the implemented DOS-P6 outcome.

| | Claude | Codex |
|---|---|---|
| discovery | in-place skills-directory plugin | local marketplace, `codex plugin add` |
| who writes vendor config | nobody | Codex's own CLI, delegated |
| install root | `~/.claude/skills/developer-os/` | `<product-home>/codex/`, distinct plugin-root and marketplace-root artifact types (§4) |
| hooks shipped | **no — neither adapter ships one (§5)** | **no** |
| hooks active on install | n/a — none ship | n/a — none ship; a trust gate would apply if they did |
| enablement source | settings read | `codex plugin list --json`, `installed[].enabled` |
| scope enforcement | `--allowedTools` | `-s <sandbox>` plus `--add-dir` |
| structured result | `--output-format json` | `--json` (JSONL, reduced — §7) plus `--output-schema` |
| probe cost | **mutating** — writes `~/.claude.json` and a backup | read-only structured query |
| probe settles | `skills` only | `skills` only |
| `plugin_hooks` | `not-used` | `not-used` |
| manifest | `{ name }` | `name`, `version`, `description`, `skills` |
| skill body | `renderSkillBody`, shared | `renderSkillBody`, shared |
| direct invocation `maxTurns` | bounded and enforced | no field; the shared `agent.prompt` parser refuses the key (§7) |
| supported floor | `2.1.142`, kept low by design | `0.147.0`, one observed version |

The capability vocabulary, the three-value model, the exit codes, the skill body and the
`agent.prompt` argument schema are **identical by construction**, and three of those five became so
during DOS-P5 rather than before it. Everything that differs is a vendor mechanism; nothing that
differs is a contract.

**The earlier cross-note debts are now reconciled.** Workflow architecture §6 records byte-identity
for both vendor artifact trees as paid. Claude architecture §9.6 records `CodexAdapter` as the
façade DOS-P5 supplied and narrows the remaining question to symmetry: neither adapter currently
needs a façade class consumed by shared code.

## 10. What the program checkpoint got, and what it did not

Program plan Task 5's checkpoint is "Claude-only, Codex-only and dual installs all work, with
explicit differences in `doctor`". **It is half met, and saying which half is the point of this
section.**

What works: the plugin installs into a real Codex installation in a disposable `CODEX_HOME`, the
marketplace registers, `codex plugin list --json` resolves our plugin to the tree we wrote, all six
skills are discoverable, uninstall reverses both CLI steps and leaves `config.toml` with neither of
our tables, and nothing is written outside the temporary homes. `doctor` reports both adapters with
their differences and emits no hook-trust advice. Earlier builds attached `/hooks` recovery text;
DOS-P6 removed it when hooks were declined.

DOS-P6 shipped the capture, ingest, and review handlers. `workflow-schema.md` §5 now lists exactly
one unimplemented vocabulary verb: `agent.prompt`, whose missing piece is a step executor rather
than adapter invocation.

The program-plan hook box records the decline rather than pretending an artifact shipped. Durable
guidance renders inside the skill rather than into an `AGENTS.md`; semantic config merge is dissolved
rather than performed; and the provisional JSONL reduction was replaced after a successful real run.

## 11. Known residuals — most with an owner, two deliberately without

1. **CLOSED by DOS-P6: the two artifact roots have distinct branded types** — §4.
   `PluginRootArtifact` cannot be passed to `proposeCodexInstall`, which accepts
   `MarketplaceRootArtifact`; the runtime location guard remains defence in depth. NEW-13 is closed.

## 12. What DOS-P8 must know

The cutover mutates the founder's live machine, and this is the only adapter that issues commands
against a vendor CLI. Two consequences:

- **A cutover must not leave a marketplace registered against a deleted directory.** Uninstall
  reverses both CLI steps *before* the tree is removed, and a failure of either step deliberately
  leaves the tree in place.
- **A re-rendered plugin tree is not necessarily a re-loaded one.** The model reads skills through
  Codex's cache copy, never the tree this adapter writes and hashes (§4, §11.14). A cutover step
  that regenerates and reinstalls the plugin must not assume the new bytes are live the moment
  install finishes — the runbook must say how to verify the cache has resynced before declaring the
  cutover done.
