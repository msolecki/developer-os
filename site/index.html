Three layers, one plugin.

Agent sessions forget everything between runs, and an agent's defaults are not a careful engineer's habits. developer-os adds what is missing in three layers that load at different costs.

Hooks that ask, never deny

Seven small hooks: two load the rules and, after a compaction, resume or fork, the state card, one shows version and vault-upkeep notices on a new session, one asks before risky commands, one notes a risky construct an edit adds, one tells the agent to stop retrying a call that failed three times, one suggests a wrap-up after a long session. They make no network calls and fail open.

It proposes. You approve. Then it acts.

Every skill that changes files, git state or anything outside your machine stops at a defined point and asks. Silence or "looks good" is not approval. The main rows are below; the full list is the approval model.

SessionStart loads

Prints the core rules; after a compaction, resume or fork, a second hook adds the state card of at most 1 KB.

PreToolUse · Bash, Edit, Write, MultiEdit asks

Asks before installs with a package argument, force pushes, git-hook bypasses, commands that destroy uncommitted work, cloud, database and publish commands, and edits of secret or agent-config files; a project can add its own questions. It never denies; in headless claude -p an ask becomes a denial.

PostToolUse · Edit, Write, MultiEdit notes

When an edit adds a known risky construct such as eval(, shell=True or verify=False, tells the agent once per pattern and file, with the safer form. It never blocks.

PostToolUseFailure reminds

At the third identical failed call within 10 minutes of the last, tells the agent to stop retrying it unchanged and find the cause.

Stop suggests

Once per long session, suggests session-retro. Reads tool-call counts and background-task ids, paths and times, never message content.

The rules load with a plain cat; the other six are Python 3 scripts with the standard library only and no network calls, and they fail open: on an error they exit silently and the normal permission flow applies. Hooks reference, privacy, security policy.

Engineering rules in every session.

An agent commits without the right checks, claims "fixed" without evidence and reviews its own code. The core rules load at session start and are capped at 8900 bytes, so they do not crowd out your own context.

Read core.md. Disagree with a rule? Override it in your own ~/.claude/CLAUDE.md, which loads alongside it.

  • Run lint, types and the changed area's tests before each commit; the full suite before a push or PR or when a skill's gate requires it.
  • Never delete or skip tests to make a build green.
  • Write a plan before changing more than 50 lines of code, and keep it current so work survives a context reset.
  • Agent-written code is reviewed by a fresh agent that did not write it.
  • "Works" and "fixed" need evidence: test output, a command result or a screenshot.
  • One git worktree per parallel agent; one orchestrator pushes.
  • Open decisions are asked as A/B/C options, not assumed.
  • Every task ends with a status: Done, Not done, Needs you.

The plugin connects moments where you already make decisions. The full loop, with what goes where, is in How to work: brain + code.

The vault is plain Markdown you own

Folders by topic (_inbox/, PROJECTS/, DEV/, TOOLS/, INFRA/, QA/, _archive/, _reports/, templates/), one frontmatter shape for every note, and Bases views for the inbox, stale notes and notes by project. brain-setup connects your existing vault by adding only what is missing; in .obsidian/types.json it adds absent keys after your approval and never changes an existing value.     Is it for you?

    A good fit if

    • you work with Claude Code across several client or product repositories, alone or in a small team;
    • you want decisions and lessons to outlive a session and a repository;
    • you are happy to review what the agent captures before it counts as knowledge;
    • you want the agent to plan, check and ask the way a careful engineer would.

    Look elsewhere if

    • you want memory that writes itself with no review: approval is the point;
    • you need a server, a search index or a shared team knowledge base: there is no runtime;
    • you want agents to merge, push to a base branch or send messages on their own: no skill does;
    • you work mainly in another agent than Claude Code: developer-os supports Claude Code only.

    Running in about five minutes.

    1. Install the plugin in Claude Code

      /plugin marketplace add msolecki/developer-os
/plugin install developer-os@developer-os

      An install takes the latest release, from main; claude plugin update developer-os@developer-os picks up later ones. Auto-update is off unless you turn it on under /plugin.

    2. Set up the vault

      Ask Claude Code to run brain-setup. After you approve the diff it adds a Brain vault: /path/to/vault line to ~/.claude/CLAUDE.md and the vault path to permissions.additionalDirectories, and asks separately whether to turn Claude Code's auto memory off ("autoMemoryEnabled": false, recommended). If you have auto memory already, brain-import-memory moves it into the vault.

    3. Open the vault in Obsidian

      Open the vault folder with “Open folder as vault” (Obsidian 1.9.10 or later). Then Settings, Core plugins: Bases and Templates, with the Templates folder set to templates.

    4. Try it

      Start a session and ask: brain-search webhooks. It should find the example note in the inbox.

    For each project, copy templates/project/ into its root; the install keeps a copy on disk, and -n skips files the project already has:

    cp -Rn ~/.claude/plugins/marketplaces/developer-os/templates/project/. /path/to/project/

    macOS or LinuxThe core rules load with cat.

    Before you install.

    Does it send my code or notes anywhere?

    The plugin sends nothing by itself and its hooks make no network calls. What the agent reads from the vault goes to your model provider as part of the session, like any file it reads. brain-capture redacts secrets before writing; review inbox notes for client names and personal data before you promote them. Privacy

    Does it change how Claude behaves in all my projects?

    Yes. The core rules load into every session in every project. Override a rule in your ~/.claude/CLAUDE.md, or disable the plugin under /plugin.

    Can I use it without a vault?

    Yes. The engineering and session skills, the agents and the hooks work on their own. The brain skills ask once for the vault path and stop if you have none, and the core rules run brain-search only when a vault is configured (the brain_vault option or a Brain vault: line).

    Can a hook block a command?

    No. The guard only asks, and on input it cannot parse it stays silent. In headless claude -p there is no one to ask, so an ask resolves to a denial.

    How much context does it cost per session?

    The core rules are capped at 8900 bytes and all skill descriptions at 12000 characters in total; scripts/check.sh fails a change that grows past either. Skill bodies load only when a skill runs.

    Is it stable?

    It is at release 0.2.9: installs follow main, which moves only on a tagged release. The changelog lists every change.

    Which language does it use?

    Skills, rules and documentation are in English, and skill descriptions carry English trigger phrasings; conventions skills load by the files you work on. The core rules keep the conversation in your language, whatever it is, and keep everything written to a repository in English unless the project says otherwise.
