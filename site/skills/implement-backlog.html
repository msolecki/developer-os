implement-backlog

Implements evidence-backed backlog items in small batches, validates every item and the whole batch, gets an independent review, updates the backlog and plan, and commits only green work.

Group
Engineering
Kind
Action
Writes
Code, the backlog (Owner lines, checked items), the plan, the state card, local commits
Asks before
Auth and security items and unscreened Check commands, once up front; the plan of an L item
Needs
A backlog in the audit-to-backlog format

When it runs

When you ask it to execute an audit backlog; free-form tasks go to parallel-lanes. It takes an optional category, task ID or --batch N.

  • fix everything with multiple agents
  • implement the backlog
  • apply the audit fixes

What it does

  1. Starts from a green baseline. It finds the backlog from the Backlog: line (otherwise TODO.md and TODO-done.md), reads it with the active plan and recent history, and runs the repository's real validation commands. A red baseline stops the run with the failures and a question.
  2. Picks the batch. By default, the ready items of the first unfinished implementation session that has any, ten at most; without sessions, the highest-priority related items, five by default and ten at most. A category prefix, a task ID or --batch N overrides that. Ready means open, every Blocked by item done, and no other Owner. Only items in the audit-to-backlog format are taken; other open lines are listed as unformatted.
  3. Asks once, up front, whether to include items that touch authentication or security boundaries, and about any Check that needs a question.
  4. Screens every Check. It never runs one that pipes into a shell, fetches from the network or writes outside the repository; that item is blocked for you to resolve. The project's own test, lint, type-check or build commands run without a question. A script in the repository is read first; one that passes the screen runs without a question, like a test command. Its result is always the command's actual output, never a verdict inferred from the source.
  5. Triages the batch. Before the claim it checks every item itself, read-only and without a delegate: its Where still exists (for an item without file:line evidence, a FEAT-, BASE- or PLAN- item, only its parent directory), its Check fails now (one that already passes means the item is done or stale; exit 126 or 127, a grep exit 2 or a "no such file" or "no tests found" message means the Check is broken, so the item is stale, not red; one that fails on authentication, quota or a missing secret makes the item blocked on you, never claimed or run again), no open pull request touches its files (skipped silently without gh or a GitHub remote), and no project decision record or doc contradicts it. An item that fails a point leaves the batch, is never claimed or dispatched, and is listed for you as stale: <ID> · <point> · <evidence> to close, amend or keep. The batch is topped up from the next ready items (within a category you named), each screened, asked about and triaged like the first ones, except when you named a single task; with no item left, the run stops and reports the stale: lines.
  6. Claims the batch. Before any brief it writes an Owner: <worktree> (<date>) line under each item and commits them as one commit, so parallel worktrees see the claim. When the backlog is git-ignored, the lines, their release and the checked-off items stay uncommitted, and the batch runs one item after another. An Owner older than 7 days is orphaned and is cleared only after you confirm.
  7. Delegates. Independent tasks with disjoint files run in parallel, each in its own git worktree at .worktrees/<id>, which git check-ignore must match before the claim (otherwise the batch runs one item after another); otherwise they run one after another. Everything is integrated on a local batch branch, and the base branch gets it only by a fast-forward after the review passes; if the base moved, both branches are left for you. The brief grows with the item's size: S gets the objective, location and Check; M also the Done when and files not to touch; L only writes a plan and returns REVIEW; you approve or reject it (see the reports below), and an unapproved L item goes under Needs you and stops for this run. Every brief carries the constraints: commit only in its worktree, never push, merge, rebase or switch branches, install nothing, stage explicit paths, and leave the backlog and the Check's files alone. Every report opens with DONE, REVIEW, BLOCKED or CONTINUING; transient failures are retried at most twice. While delegates run, it only orchestrates.
  8. Reads the reports. On DONE it runs the Check itself in the delegate's worktree, then again after integrating (a sequential item once, in the current checkout); a Manual: item is committed but stays open without its Owner, with steps for you to confirm; REVIEW shows the plan and asks you; an approved plan is saved as docs/plans/approved/<ID>.md (never read as the active plan, deleted when the item is done) and the item is dispatched again as M with it (a later run does the same for an L item whose plan file exists), while a rejected or unanswered plan goes under Needs you; BLOCKED on you goes under Needs you, on another item releases the claim and proposes a Blocked by: line, and on the orchestrator gets one more dispatch with the missing input before it counts as blocked on you; CONTINUING is dispatched again. A report without a status goes back once.
  9. Validates. The item's Check after every item, then the full build, type check, tests and lint for the batch, showing only failures. Test failures are classified before editing; assertions change only for a contract that changed. A wrong Done when, or an item whose code no longer matches it (a moved file, a changed API, a branch that landed since), stops that item and gets a proposed Amended line, never an edit. Three failed repair cycles stop the run in a deployable state. A short state card in docs/plans/.devos-state.md survives a context compaction.
  10. Reviews and records. The batch diff goes through code-review and the independent reviewer agent. It fixes confirmed P0/P1 and docs findings itself, for at most two review rounds; a P0/P1 whose fix neither the item's Done when nor the spec settles goes to you as an intent gap instead of a patch. The review passes on APPROVE, or on a COMMENT whose question you answered; without a pass the base branch gets nothing and the batch branch is left for you. When the batch closes the last open item that cites a spec, it runs a convergence check: each acceptance criterion against the code, on three levels (exists, not a stub, wired into a caller), a manual check counting as unverified; each gap is proposed as a FEAT- item for your approval. Other findings are proposed as backlog items for your approval; done items move to the done file with their Check result. It stages only batch files; the record commit (backlog, done file, plan, and the cleared Owner lines of items still open) waits until everything passes, then reports one line per item (a blocked item with its unblock owner and the output that shows the block) and the next batch.

Example output

docs/plans/.devos-state.md
Plan: docs/plans/2026-10-15-checkout-retry.md
Item: CART-12 (in progress)
Agents: .worktrees/cart-13 → CART-13, .worktrees/cart-14 → CART-14
Status: clean | watch <risk> | blocked <on what>
Not started: <what looks begun and is not: no branch, no edit, no commit>
Not verified: <checks not run; never fold them into a pass>
If: <X> then <Y> (a failure the next session will hit)
Next: <one line>

Boundaries

Stops when

The batch is committed locally, or earlier at a red baseline, after three failed repair cycles, or after two review rounds without a pass. It deletes the state card and returns the validation evidence, the review additions and the next batch. On any stop, even before claiming, each item found blocked is reported as <ID> · BLOCKED · Unblock owner: … with the command and output that show the block, and each item the triage dropped as its stale: line. Claimed items still open lose their Owner line in the record commit when the batch lands, otherwise in a release commit on the base, made from a clean checkout of the base while the batch branch stays untouched for you, so the next run can take them.

Never

  • Claim, dispatch or start an item that failed the triage.
  • Push or force-push, rebase a shared branch or merge into one other than by --ff-only, or open a PR; the only writes to the base are the claim and release commits and the local git merge --ff-only of the batch branch after the review passes.
  • Include authentication or security items you did not approve up front.
  • Delete or skip tests, or change assertions for a contract that did not change.
  • Commit red work or files outside the batch, other than the docs a docs finding named and the Owner claim and release commits, which touch only the backlog file.
  • Edit or delete a Done when, or take an item another worktree owns.
  • Implement a backlog item itself while a delegate is running.
  • Dispatch or start an item before its Owner line is committed (only written, when the backlog is git-ignored), or force-add an ignored backlog file.
