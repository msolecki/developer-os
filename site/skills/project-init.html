Skills / Project hygiene

project-init

Adopts developer-os in a repository in one pass: it detects the stack, picks the skills that apply, runs the setup skills and a conventions audit, and gives one report with one question. Nothing is written before you answer it.

Group
Project hygiene
Kind
Action
Writes
Approved items only: backlog items, doc edits, the instruction-file diff
Asks before
Applying any item; it never picks a default for a decision

When it runs

When you start using developer-os in a repository, or want the whole project checked at once. Say it in your own words, for example:

  • init developer-os here
  • check the whole project
  • set the repo up for developer-os

What it does

It is an orchestrator: each skill it runs keeps its own steps and its own rules, and their results are merged into one numbered list.

  1. Reads the context. The stack from the manifests and config on disk (lockfile, tsconfig.json, next.config.*, test files, CI, infrastructure code, API routes, a database and migrations, a UI), the backlog files (without them, their paths are a decision for you, and the Backlog: line is a numbered item), and the project's AGENTS.md, docs/pitfalls.md and decision records: anything the project rejected on purpose is reported as deliberate.
  2. Picks the skills. project-baseline and docs-sync always; instruction-review when a CLAUDE.md or AGENTS.md exists; each conventions skill when its stack is present. comments-conventions is never audited (it governs only comments an agent adds); deploy-checklist is never run (it runs the project's gates and belongs to a release).
  3. Runs the process skills. project-baseline, docs-sync and instruction-review, each up to its report, collecting their items instead of asking their questions one by one.
  4. Audits the conventions. One probe per rule, such as "strict": true in tsconfig.json, an empty catch {}, date fixtures without Z, mock factories that do not spread the original module, or a /health handler that queries the database. Rules that need judgment are sampled: at most five file:line cases per rule. Each P0 and P1 finding goes to a fresh verifier, as in audit-to-backlog. Findings become CONV-NN backlog items; an unsure result is a question.
  5. Reports and asks once. The stack, which skills applied and which did not, one numbered list across all of them, and one A/B/C question.

Boundaries

Stops when

It has shown the report and asked its question. After your approval it applies exactly the approved items the way the owning skill applies them, shows git diff --stat and stops; fixing the findings is implement-backlog's job, and you commit.

Never

  • Write, create or delete any file before you approve the numbered items.
  • Change application code, tests, configuration or existing comments.
  • Run the project's scripts, tests or builds, install dependencies, or run deploy-checklist.
  • Pick a default for a "needs your decision" item, or propose something the project rejected on purpose.
  • Commit, push or open a pull request.

Related
