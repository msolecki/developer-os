Workflow at a glance

An agent session forgets. The vault remembers. You decide what stays. developer-os connects every session to two durable places: an Obsidian vault for knowledge that outlives the project, and the repository for the plan and the code. New knowledge enters through _inbox/ and becomes trusted only after you approve it.

vault knowledge into the session a new decision into _inbox/ plan and code into the repository

Three layers, one plugin

Agent sessions forget everything between runs, and an agent's defaults are not a careful engineer's habits. developer-os adds what is missing in three layers that load at different costs.

memory

A vault that remembers

Decisions, lessons and references live in an Obsidian vault of plain Markdown. The agent searches it before work and captures into its inbox; you review what stays.

  • Writes outside the inboxonly on approval
  • Deletesnever, archives
operating model

Habits of a careful engineer

Core rules in every session, workflow skills that stop at defined points, conventions that load only for matching files, and specialist agents for independent passes.

  • Core rulesat most 8900 bytes
  • Skill bodiesload when a skill runs
guard rails

Hooks that ask, never deny

Seven small hooks: two load the rules and, after a compaction, resume or fork, the state card, one shows version and vault-upkeep notices on a new session, one asks before risky commands, one notes a risky construct an edit adds, one tells the agent to stop retrying a call that failed three times, one suggests a wrap-up after a long session. They make no network calls and fail open.

  • Network callsnone
  • On a parse errorexit silently

The daily loop

A rhythm, not another tool to babysit: the plugin connects moments where you already make decisions. Nothing in the loop runs on its own: you start every skill. Hooks only remind and guard. Select a step, or let the loop play. The full text is in How to work: brain + code.

    A one-line notice at the start of a new session reminds you when inbox notes are older than a week or brain-garden has not run for a month.

    The vault is plain Markdown you own

    Folders by topic (_inbox/, PROJECTS/, DEV/, TOOLS/, INFRA/, QA/, _archive/, _reports/, templates/), one frontmatter shape for every note, and Bases views for the inbox, stale notes and notes by project. brain-setup connects your existing vault by adding only what is missing; in .obsidian/types.json it adds absent keys after your approval and never changes an existing value.     Hooks in one session

    Small Python scripts with no dependencies and no network. They ask instead of blocking, and stay silent when they fail. Details are in the hooks reference.

    What the timeline leaves out:

    • The guard asks before installs with a package argument, force pushes, git-hook bypasses, commands that destroy uncommitted work and edits of secret or agent-config files; a project can add its own questions. It never denies; in headless claude -p an ask becomes a denial.
    • The risky constructs are ones such as eval(, shell=True or verify=False; the agent is told once per pattern and file, with the safer form.
    • The failure reminder comes at the third identical failed call within 10 minutes of the last.
    • The state card is at most 1 KB.
    • The Stop hook reads tool-call counts and background-task ids, paths and times, never message content.

    The rules load with a plain cat; the other six are Python 3 scripts with the standard library only and no network calls, and they fail open: on an error they exit silently and the normal permission flow applies. Hooks reference, privacy, security policy.

    Engineering rules in every session

    An agent commits without the right checks, claims "fixed" without evidence and reviews its own code. The core rules load at session start and are capped at 8900 bytes, so they do not crowd out your own context.

    • Run lint, types and the changed area's tests before each commit; the full suite before a push or PR or when a skill's gate requires it.
    • Never delete or skip tests to make a build green.
    • Write a plan before changing more than 50 lines of code, and keep it current so work survives a context reset.
    • Agent-written code is reviewed by a fresh agent that did not write it.
    • "Works" and "fixed" need evidence: test output, a command result or a screenshot.
    • One git worktree per parallel agent; one orchestrator pushes.
    • Open decisions are asked as A/B/C options, not assumed.
    • Every task ends with a status: Done, Not done, Needs you.

    Read core.md. Disagree with a rule? Override it in your own ~/.claude/CLAUDE.md, which loads alongside it.

    From idea to merge

    The repository remembers the code. The plan lives in docs/plans/ and is deleted once every step is in a commit; a reviewer other than the author checks the work before it merges.

    spec→ audit-to-backlog→ implement-backlog→ code-review→ pr-cycle→ docs-sync→ session-retro

    Vault or repository? A decision, lesson or reference that you or another project will look for again goes to the vault. A plan, an ADR or a fact about the code stays in the repository: a plan in the vault drifts away from the code it describes. See Vault or repository?

    Is it for you?

    A good fit if

    • you work with Claude Code across several client or product repositories, alone or in a small team;
    • you want decisions and lessons to outlive a session and a repository;
    • you are happy to review what the agent captures before it counts as knowledge;
    • you want the agent to plan, check and ask the way a careful engineer would.

    Look elsewhere if

    • you want memory that writes itself with no review: approval is the point;
    • you need a server, a search index or a shared team knowledge base: there is no runtime;
    • you want agents to merge, push to a base branch or send messages on their own: no skill does;
    • you work mainly in another agent than Claude Code: developer-os supports Claude Code only.
