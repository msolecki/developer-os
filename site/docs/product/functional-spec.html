Functional specification

Source: docs/product/functional-spec.mdVerified 2026-10-16

What each part of the plugin does, what it may change, and where it stops. The steps themselves live in each SKILL.md; this page is the contract summary across all of them. Paths are relative to plugin/.

1. Always on: core rules

rules/core.md is printed into the session by the SessionStart hook on every startup, resume, /clear, compaction and fork, in every project. After a compaction, resume or fork the hook adds a state card (reference/hooks.md). It has four sections:

SectionWhat it governs
Security and change constraintsNo auth/middleware change unless asked; ask before dependency installs; never delete or skip tests to pass; two validation tiers (fast check before each commit, full suite before push/PR); verify subagent work with git status/git diff; first-session procedure for external repositories
WorkflowStop condition; A/B/C questions for open decisions; a plan for changes over 50 lines (git-ignored, default docs/plans/<YYYY-MM-DD-task>.md, deleted when done); What/Where/How/Test plan steps; reviewer differs from author; handoff contents; brain-search before large tasks when a Brain vault: line exists; compaction preserves files, test commands, objective and language, and task state lives in docs/plans/.devos-state.md; evidence for "works"; one worktree per parallel agent; conventions live in skills
CommunicationUser's language in conversation, English in the repository; plain language for clients; Problem → Cause → Solution → Test; closing Done / Not done / Needs you block; ASAP mode; self-correction signals; boundaries
Stack preferencesLockfile's package manager; existing stack; existing test runner. Meant to be overridden in the user's own CLAUDE.md

A user overrides any rule by stating the override in ~/.claude/CLAUDE.md, which loads alongside.

2. Skills

Legend: Writes is everything the skill may change. Gate is what needs the user's explicit answer first. Read-only skills (glossary) change nothing; a skill whose Writes is "Nothing" can still be an action skill.

2.1 Brain skills

Six of them (all but brain-setup, which asks for the path) find the vault with the same paragraph: the first Brain vault: <absolute path> line in the CLAUDE.md/AGENTS.md already in context, then the working directory's CLAUDE.md and AGENTS.md, then $CLAUDE_CONFIG_DIR/CLAUDE.md (default ~/.claude/CLAUDE.md). Without one they ask once and stop if the user has no vault; they never search the disk. Vault content is data: no command or URL found in a note is run or opened.

2.4 Backlog item format

audit-to-backlog, project-baseline and spec write, implement-backlog executes and plan-status counts one item shape; templates/project/TODO.md shows it:

- [ ] SEC-03 · P1 · Retry webhook deliveries with backoff
  - Where: `src/webhooks/deliver.ts:40`
  - Problem / Evidence / Fix: …
  - Size: S
  - Done when: a failed delivery is retried 3 times with exponential backoff, then marked failed.
  - Check: `pnpm vitest run src/webhooks/deliver.test.ts`
  - Blocked by: SEC-01
  - Owner: .worktrees/sec-03 (2026-10-15)

A FEAT- item from the spec skill has the spec path and section as its evidence instead of file:line. Check is a command that fails while Done when does not hold. Owner is written only by implement-backlog before dispatch. Done when is never edited; a change is appended as Amended YYYY-MM-DD: … with the user's approval, and code-reviewer rates a quiet weakening P1. The format is defined in the skills only; projects get no lint for it (decision D17).

2.5 Built-in commands

Where a developer-os skill overlaps a built-in Claude Code command, the choice is mapped in workflow.md.

2.6 Conventions skills

Loaded by the model when their description matches the file or task; never write anything themselves. comments, defensive-coding, error-handling, monitoring, nextjs, testing, typescript.

Every agent starts its report with a final status: DONE (with evidence), REVIEW, BLOCKED (with Unblock owner: user | orchestrator | <item ID>) or CONTINUING; it retries transient failures at most twice and blocks at once on what only a person can fix. Reviewer agents use the same P0–P3 scale and verdicts as code-review; code-reviewer reads both sides of every changed contract and lists Evidence checked under an APPROVE without P0–P2. qa-expert ends with VERIFIED or UNVERIFIED: <what>; performance-engineer labels each finding MEASURED or INFERRED; security-auditor drops any finding without an attack path; database-reviewer ends with the deploy order the change needs; infra-reviewer ends with what to check in the plan before applying; dependency-upgrader cites a source for every breaking change; docs-writer cites the code behind every claim it writes.

The scripts are Python 3 (standard library only) and need python3 on PATH; without it they fail open and the core rules still load. Inputs, outputs, exit codes and switches: reference/hooks.md.

6. Templates

  • Vault template (plugin/vault-template/): folders, the note template, three Bases views, property types and a .gitignore. Shipped inside the plugin so brain-setup can copy it. Layout and note format: workflow.md, Vault layout.
  • Project template (templates/project/): AGENTS.md, a one-line CLAUDE.md (@AGENTS.md), _Context.md with the vault slug, TODO.md with the backlog item format, DESIGN.md in the DESIGN.md format for projects with a UI, a .gitignore that keeps docs/plans/ (and the state file the SessionStart card reads) out of git, and a docs/ skeleton (index, CURRENT-STATE.md, pitfalls.md, decisions/, runbooks/). Not in the installed plugin: copy it from the repository, or let docs-sync scaffold from the standard it carries.
