Decisions

Source: docs/product/decisions.mdVerified 2026-10-16

One register for the plugin era. Each entry: date, decision, why, and the commit that put it in the code. Alternatives are listed only where the history records them. Never renumber; when a decision is replaced, mark it superseded and add a new entry. Decisions of the CLI era are not carried over; their history is at the git tag archive/cli-v0.

D1. Plugin only

  • Date: 2026-10-14 · Commit: 19e4f61a
  • Decision: developer-os is a Claude Code plugin of Markdown and JSON. The CLI, its bundled Node runtime, background jobs, generated indexes and Homebrew tap are removed.
  • Why: the CLI had grown to roughly 125k lines and a multi-hour validation gate to deliver what skills, rules and the agent's own file tools already do.

D2. No runtime; small hook scripts without dependencies

  • Date: 2026-10-14, extended 2026-10-15 and 2026-10-16 · Commits: 53504f88, 1c324a89
  • Decision: the only executable code is the hook layer: cat of the core rules, plus capture-nudge.sh and guard.sh in POSIX sh, without jq, without network calls.
  • Why: anything that runs in every session of every user must be small enough to read in full and must not add dependencies.
  • Amended 2026-10-15: a third script, session-start.sh, replaces the inline cat (D16), and scripts/install-codex.sh runs only by hand, outside the plugin (D19).
  • Amended 2026-10-24: scripts/install-codex.sh is removed (D21).
  • Amended 2026-10-16: the hook scripts are Python 3 (3.8+, standard library only, no network): state-card.py, guard.py and capture-nudge.py replace the sh scripts and guard.awk. The Claude plugin directory's validator reads the shell scripts a hook runs and refuses any command whose path the shell computes (a variable other than ${CLAUDE_PLUGIN_ROOT}, a command substitution, a glob) or any inline program; the hooks need paths outside the plugin (the project's cwd, the transcript, a temporary directory). Scripts in other languages are held for a human reviewer instead of refused. The core rules load through a literal cat hook again, so they never depend on Python; without python3 the other three hooks fail open.
  • Amended 2026-10-24: a fourth script, notices.py, on SessionStart startup (D22).

D3. The vault is read and written with the agent's own file tools

  • Date: 2026-10-14 · Commit: 255c798e
  • Decision: brain skills use rg, find, Read, Write and Edit on plain Markdown. No index, no search server, no database.
  • Why: rg over plain Markdown is enough for a personal vault; an index is one more thing to rebuild and drift. It replaces the CLI's brain reindex and brain search.

D4. The agent writes only to _inbox/; archive, never delete

  • Date: 2026-10-14 · Commits: 369028cc, 0c4ab694, 9242bf87
  • Decision: agent-created notes go to _inbox/ with status: inbox. Any other edit, move, merge or archive happens only for notes the user names. Retired notes move to _archive/ with status: archived; nothing is deleted.
  • Why: an unreviewed agent note is a draft, not a fact; approval is the one step that keeps the vault trustworthy. Archiving keeps mistakes recoverable.

D5. Find the vault through a Brain vault: line

  • Date: 2026-10-14, lookup order extended 2026-10-15 · Commits: 255c798e, f8c6eac3
  • Decision: the vault path is one line, Brain vault: <absolute path>, in a CLAUDE.md or AGENTS.md. Skills look in context, the working directory, ~/.claude/CLAUDE.md and ~/.codex/AGENTS.md, ask once if it is missing, and never search the disk.
  • Why: works identically in Claude Code and Codex with no plugin configuration mechanism.
  • Amended 2026-10-24: the lookup no longer reads ~/.codex/AGENTS.md (D21).
  • Open: replacing the line with the plugin's userConfig is under consideration (a local, git-ignored proposal, not in the repository).

D6. Hooks ask, never deny, and fail open

  • Date: 2026-10-15 · Commit: 1c324a89
  • Decision: the guard answers ask for its three categories and nothing else; both scripts exit silently on input they cannot parse or on any error.
  • Why: a broken guard must not block a session; an extra confirmation costs one click, while a missed install rewrites a lockfile. Per the README, an ask resolves to a denial in claude -p, the safe default for headless runs.
  • Amended 2026-10-30: a fourth category, commands that destroy uncommitted or untracked work (rm with a recursive and a force flag, git reset --hard, git clean -f, git checkout/git restore of the whole tree, git worktree remove --force). Users without their own deny list had no check on these in auto mode; they are the first reflexes harness-engineering-101 (chapter 13) names.
  • Amended 2026-10-30: a fifth category, an Edit or Write of a secret file or the user-level agent config (.env*, ~/.ssh, ~/.aws, ~/.gnupg, ~/.claude.json, ~/.claude/settings*.json, ~/.claude/hooks, ~/.claude/rules). The rule against copying hooks into ~/.claude unread was prompt-only.
  • Amended 2026-10-30: a sixth category, a writing Bash call inside the five read-only review agents, keyed on the hook input's agent_type. They keep Bash for git diff and test runs; permissionMode is ignored for plugin agents, and disallowedTools: Bash would remove those reads.
  • Amended 2026-10-30: a git commit that hits no category gets additionalContext (no decision) reminding the agent of the fast check; a rule loaded at session start fades in a long session, and a reminder tied to the event it governs does not (harness-engineering-101, chapter 8). Checked in claude -p: the text reaches the model and the command runs without a prompt.
  • Scope, 2026-10-30: the guard matches command text, so it decides what asks; it is not a security boundary. The boundary is Claude Code's permission rules and sandbox (Harness Patterns 2.14 Proxy: text patterns are easy to get around with quoting, aliases or scripts).
  • Amended 2026-10-31: the destroy category adds git stash drop/clear (a dropped stash is gone short of git fsck); a restore or checkout of one path still passes, since undoing one file is routine and an ask on each would be noise. The protected files add ~/.claude/CLAUDE.md and ~/.claude/agents, skills and commands, which load into every session like rules; a brain-setup or session-retro line written there now costs one click. In the read-only agents, --write, --fix and snapshot updates ask, the commonest way a reviewer that runs lint or tests rewrites files.
  • Amended 2026-10-31: the protected files add .envrc (direnv secrets) and the same config under $CLAUDE_CONFIG_DIR, which moves it for a second account. In the read-only agents, unlink, rmdir and patch ask, and the word after an option's value is checked as a command too, so xargs -I{} rm (whose {} a view drops) asks.
  • Amended 2026-10-31: the destroy and read-only categories match only a command in command position, so a mention in an argument (grep -rn "rm -rf", git commit -m "… reset --hard", grep -rn "git add" in a reviewer) no longer asks; a reviewer greps for command text on every review of hooks or docs. Command position now also follows timeout, nice, stdbuf, doas, eval, a shell keyword (then, do, …), a shell's or su's -c, and the wrappers that ran a command before (watch, setsid, flock, chroot, …), so sh -c "git reset --hard" still asks; a command on another host or in a container (ssh, docker exec) no longer does. git rm -f asks, since it removes files with uncommitted changes. The install, push and hook-bypass categories still ask on a mention.

D7. One wrap-up nudge per long session

  • Date: 2026-10-15 · Commit: 1c324a89
  • Decision: the Stop hook asks for session-retro once per session after 30 tool calls, skipping headless/SDK runs and subagents, and deferring while a background task it launched is still running (PR #69). It counts entries and reads background-task ids and output paths, never message content.
  • Why: lessons are lost at the end of long sessions, but a nudge on every stop is noise.
  • Superseded draft: the first design nudged brain-capture directly; session-retro replaced it because it routes each finding to its destination, the vault being only one of them.

D8. One severity scale and a fresh verifier

  • Date: 2026-10-15 · Commit: 9d4319d8
  • Decision: every review, audit and triage skill and every reviewer agent rates P0–P3 with the same definitions; verdicts are APPROVE, COMMENT, REQUEST_CHANGES. code-review and audit-to-backlog send each P0/P1 finding to a verifier that sees only the claim (Codex when its plugin is installed, otherwise a fresh subagent); refuted findings move to a Disputed list.
  • Why: one scale makes findings comparable across skills; a verifier without the reviewer's reasoning catches confident false positives before they block a merge.
  • Amended 2026-10-24: the verifier is always a fresh verifier agent; the Codex option is removed (D21).

D9. Action skills declare where they stop and what they never do

  • Date: 2026-10-15 · Commit: 1c324a89
  • Decision: every skill that can write, send or change git state ends with ## Stop point and ## Never. Read-only skills (brain-search, code-review, plan-status, skill-usage) and *-conventions are exempt. scripts/check.sh enforces it.
  • Why: the stop point and the forbidden side effects are the contract a user relies on; a check keeps new skills from omitting them.

D10. Fixed per-session budget

  • Date: 2026-10-15 · Commits: c8129daf, 1c324a89
  • Decision: plugin/rules/core.md is at most 8192 bytes; each skill description is 80–1024 characters and all descriptions together at most 12000.
  • Why: both load into every session; SessionStart hook output is capped at 10,000 characters.

D11. Plans are local

  • Date: 2026-10-14 · Commits: 2efedc27, 0c4ab694
  • Decision: plans live in a git-ignored planning location (default docs/plans/) and are deleted when done, with open items moved to TODO.md or the backlog. A project may override this in its AGENTS.md. This repository's docs/plans/ is git-ignored.
  • Why: a committed plan goes stale the day the task ends; a plan in the vault drifts from the code.

D12. Codex is manual and best-effort (superseded by D19)

  • Date: 2026-10-14 · Commit: 369028cc
  • Decision: no Codex manifest. Users copy skills to ~/.agents/skills/ and paste the core rules into ~/.codex/AGENTS.md. Not tested on releases.
  • Why: the skills need only file and shell tools; hooks, agents and output styles have no Codex equivalent worth maintaining.

D13. Evals run by hand, never in CI

  • Date: 2026-10-15 · Commit: 1c324a89
  • Decision: evals/ holds claude plugin eval cases with a with-plugin and a baseline arm; they run by hand before a release or after changing a tested skill.
  • Why: every run spends real plan usage (two agent sessions per case and run, plus judge calls).

D14. development is the default and install branch (superseded by D20)

  • Date: 2026-10-14
  • Decision: /plugin marketplace add msolecki/developer-os installs from development, the repository's default branch. main is not the release channel today.
  • Pinning: a user holds one version by adding the marketplace at a branch or tag (/plugin marketplace add msolecki/developer-os#<ref>); no release tag exists yet.
  • Open: a release procedure (tags, changelog date).
  • Amended 2026-10-15: plugin.json carries no version. Claude Code then versions an install by the commit SHA, so claude plugin update picks up every commit on development, docs-only ones too. The pinned 0.1.0 kept every install on its first cached copy, whatever was pushed later.
  • Superseded 2026-10-16 by D20.

D15. Language split

  • Date: 2026-10-14
  • Decision: the agent converses in the user's language and keeps it after English input, subagent reports and compaction; everything that lands in a repository is English unless the project says otherwise. Skill descriptions, examples and evals are English only.
  • Why: repositories and the public plugin are English, and a public plugin should not depend on one user's language to fire.
  • Amended 2026-10-16: the non-English trigger phrases in skill descriptions, skill examples and evals were replaced with English ones; the conversation rule is unchanged.

D16. Task state survives compaction in the plans directory

  • Date: 2026-10-15 · Sources proposal #2, Q10
  • Decision: after a compaction or resume, the SessionStart hook appends a state card (branch, newest plan, docs/plans/.devos-state.md, worktrees) of at most 1024 bytes. Orchestrating skills keep the state file current. It lives in docs/plans/, already git-ignored.
  • Why: the compaction summary drops which item, worktree and unverified claim belong to which agent; the hook already re-runs on compaction, so no new event is needed.
  • Hardened after review: the state file is shown only when untracked, git-ignored and reached without a symlink, and a tracked plan is not named, so a cloned repository cannot inject instructions through them or point the card at a local secret; the branch name still prints (git forbids spaces and control characters in it).
  • Amended 2026-10-15: the state file prints before the worktree list, so a long list cannot push it past the cap; a card over the cap is cut at a whole line with a marker; a state file not changed in 7 days is left over from a finished run and is not shown. The card's Newest plan: line comes from the plan files only; the state file's own Plan: line prints inside the state section.
  • Amended 2026-10-16: the state-file path is fixed at docs/plans/.devos-state.md even when a project overrides its planning location; skills and core rules name that path. A project that moves its plans still git-ignores docs/plans/ (or that file) so the card shows it — the one extra .gitignore entry D16 rejected .claude/devos-state.md for.
  • Amended 2026-10-16: the card comes from its own hook, state-card.py, matched to compact and resume; the core rules print from a separate cat hook (D2), so the card is no longer guaranteed to follow them.
  • Amended 2026-10-24: the state card also runs on a forked session (source fork).
  • Rejected: a PreCompact hook (its input and output are undocumented); .claude/devos-state.md (one more .gitignore entry per project).

D17. One backlog item format, defined in the skills only

  • Date: 2026-10-15 · Sources proposal #3, Q11
  • Decision: backlog items carry Size, Done when, a runnable Check, Blocked by and Owner; Done when changes only by an appended Amended line. The skills write and read the format; no lint is proposed to projects yet.
  • Why: parallel agents took the same or blocked items, and implementers could lower a criterion to pass. A project lint waits until plan-status shows the format drifting.

D18. agnix in CI only, pinned

  • Date: 2026-10-15 · Sources proposal #13, Q12
  • Decision: CI downloads the agent-sh/agnix v0.57.0 release binary, checks it against a SHA-256 in the workflow, and runs it strict, with suppressions in .agnix.toml, each with its reason. scripts/check.sh adds plugin/SURFACE.txt and digit-count checks, which need no new tool.
  • Why: a local agnix would need an install on every contributor's machine. The hash lives in the workflow because the action's own checksum file comes from the same release and proves nothing if the release is replaced.

D19. A Codex installer that copies, not symlinks (superseded by D21)

  • Date: 2026-10-15 · Sources proposal #15, Q13
  • Decision: scripts/install-codex.sh, run by hand, writes a Codex copy of every skill (name and a short description only, Claude-only references rewritten, a .developer-os-codex marker) and keeps the core rules and the Brain vault: line between markers in ~/.codex/AGENTS.md. No Codex hooks.
  • Why: Codex lists skills within 8000 characters by default (the installer counts bytes, which are never fewer than characters); the full descriptions are over 10,000 characters (the scripts/check.sh descriptions stage counts characters), so a symlink cannot fit and a copy must carry a shorter description. Pasting core.md by hand went stale silently; a marked block is replaced in place and backed up. Codex's documentation does not confirm the hook events the guard needs.
  • Rejected: symlinks for skills without Claude-only references (the budget still overflows); installing guard.sh for Codex.

D20. Versioned releases from main

  • Date: 2026-10-16
  • Decision: main is the default branch and the marketplace channel; it moves only on a release, a fast-forward from development. Both manifests carry the same version, bumped on every release and tagged v<version>. The first release is 0.1.0.
  • Why: with the public launch, an install should change only when a release does, not on every docs commit; the cached-copy problem of D14 is the intended behaviour once main moves only on a release. Anthropic's plugin directory warns on a missing version. Same model as founder-os.
  • Alternatives: a tag on development without a version (installs keep tracking every commit).

D21. Claude Code only

  • Date: 2026-10-24
  • Decision: developer-os supports Claude Code only. scripts/install-codex.sh and its test are removed, the brain skills no longer read ~/.codex/AGENTS.md, and code-review and audit-to-backlog always use the verifier agent instead of the Codex plugin. Supersedes D19.
  • Why: the maintainer's decision; reason not recorded.

D22. Version and upkeep notices instead of a schedule

  • Date: 2026-10-24
  • Decision: a SessionStart hook on startup, notices.py, shows the user one-line notices: the version and a link to the changelog page on the first session after an install or update (a version marker in ${CLAUDE_PLUGIN_DATA}), inbox notes older than 7 days (at most weekly) and no brain-garden run in 30 days (at most monthly). It runs no skill and creates no routine; the docs say plainly that vault upkeep does not run on its own. The vault path comes from the user-level CLAUDE.md only, and the notices carry counts and dates, never note names.
  • Why: users could not tell whether review and garden happen by themselves. Claude Code has no install or update hook, a plugin cannot create a routine, and a cloud routine does not load the plugin's skills, so a reminder where the user already works is the only mechanism inside the plugin (D2: no runtime, no network). Claude Code shows nothing from a plugin's changelog on update.
  • Alternatives: docs only (users still miss it); creating a routine at setup (not possible from a hook, and it would act without asking, against D6); printing changelog entries in the terminal (needs a copy of CHANGELOG.md inside plugin/ on every release; a link is enough).

D23. Parallel lanes are headless sessions the user approves

  • Date: 2026-10-25
  • Decision: the parallel-lanes skill runs each lane as a separate claude -p process in its own git worktree and branch, started detached (setsid through python3, which the hooks already require) so it outlives the turn, with --permission-mode acceptEdits and an explicit --allowedTools list. It launches only after the user approves the shown launch.sh; lanes commit in their worktree and never push, merge or install; the launching session integrates finished lanes into a local branch and reviews them through code-review.
  • Why: subagents run inside the session that dispatched them and end with it, while long lanes need to keep running and be watched from a later turn. A permission bypass would let an unattended process run any command, against the approval model; a fixed tool list makes a lane that needs more stop as BLOCKED instead.
  • Alternatives: dispatching lanes as subagents (implement-backlog's model, kept for backlog items); --dangerously-skip-permissions (rejected for the reason above); nohup alone (the lane stays in the harness's process group, which kills background jobs after about 29 minutes).

D24. The vault is the one long-term store; auto memory is off by recommendation

  • Date: 2026-10-26
  • Decision: developer-os recommends "autoMemoryEnabled": false in the user's settings.json. brain-setup offers it as a separate yes/no; session-retro no longer routes anything to auto memory (user preferences go to the user-level CLAUDE.md); the brain-import-memory skill moves an existing auto-memory folder into the vault item by item (new inbox notes, additions to notes the user names, preference and project-rule lines) and never edits or deletes the memory files.
  • Why: auto memory is a second store per project and machine that the agent writes without review, with its index loaded into every session. It duplicated vault notes and drifted from them, could not be searched across projects or read by other agents, and bypassed the approval step D4 puts on vault knowledge. On the author's machine it held more than 500 files across 20 projects when this was decided.
  • Alternatives: keeping both stores with a routing table (the 0.2 behaviour; facts still landed in both); pointing autoMemoryDirectory at the vault (one shared folder for every project, written without review, outside the vault's note format); copying all memory files into _inbox/ in one go (skips brain-capture's gate and floods the inbox).

D25. Every agent has a turn cap

  • Date: 2026-10-30
  • Decision: each plugin agent sets maxTurns: 100, and 40 for verifier, which checks one claim. At the cap Claude Code (v2.1.246 or later) returns the agent's output marked partial; audit-to-backlog then names the missing dimension instead of presenting the backlog as complete.
  • Why: a one-line Agent call hides an unbounded subagent (Harness Patterns 2.18 Delegation); a reviewer stuck re-running a failing command spent tokens with no limit. The cap is a runaway stop, not a budget: an ordinary review stays well under it.
  • Alternatives: effort per agent (changes quality, not the upper bound); no cap (the status quo).

D26. A repeated failure gets one reminder

  • Date: 2026-10-30
  • Decision: a PostToolUseFailure hook counts failures per session by a hash of the agent, tool and input (for Bash, the command) and, at the third failure of the same call, adds additionalContext telling the agent to stop retrying it unchanged. A failure more than 10 minutes after the previous one of that call starts a new count. Once per run of failures, no decision, fail open (D6).
  • Why: a model that keeps calling the same failing tool is the commonest runaway loop (Harness Patterns 1.01 Game Loop); a rule loaded at session start fades, a reminder tied to the event does not. Checked in claude -p: a non-zero Bash fires the event and the text reaches the model.
  • Alternatives: two failures (the second retry of a flaky command is often legitimate); counting the whole session (a test run that is red now and then over an hour is not a loop); resetting on success (a second hook on every tool call); a PostToolUse hook (it does not fire for a failed call); a rule in core.md (no room, and it fades).
  • Amended 2026-10-31: a success does not reset the count, so a test run that is red, green and red again within 10 minutes during test-first work reaches three. The message says so ("each within 10 minutes of the last") and tells the agent to stop only if nothing changed between the runs; a reset on success would cost a hook process on every Bash call.
